- **Affiliations:** UMass Amherst, Zoom (work done as interns at Zoom Video Communications), Emory University, UNC Charlotte.

- **Peer review:** Preprint. We found no sign of peer review.

### 1.1 What they built (§2)

- A small harness, built on LangGraph, with a fixed ReAct loop. Benchmarks run through Harbor (§3.1).
- Three parts change. All other parts stay fixed:
  - **Planning (§2.1):** an `update_plan` tool. The harness puts the current plan into each turn. The plan is not stored in history (Fig. 17).
  - **Action space (§2.2):** (a) predefined tools `read_file`, `write_file`, `edit_file`, `list_files`, `glob_files`, `grep_text`, `web_fetch`, `bash` (Table 1); or (b) bash only. No web search, because it can leak the SWE-Bench fix.
  - **Context management (§2.3, Table 2, Alg. 1):** five tiers.
    - T0: none. The run stops on overflow.
    - T1: elision (M1). Old, large tool outputs become a short stub.
    - T2: elision plus recall (M2). Originals go to a store. A `recall_event` tool gets them back.
    - T3: LLM summary (M3) only.
    - T4: M1 at a soft limit (0.6 of window), M3 at a hard limit (0.85). Recent turns (0.3 of window, at least 2 turns) stay verbatim.
- **Fixed parts (§2.4, App. A.4):**
  - Path guard (no escape from project root, symlinks too).
  - Read-before-write check with content hash.
  - Permission layer: allow / ask / deny. Tool errors go back to the model as observations.
  - Post-edit diagnostics: ruff, pyflakes or a syntax check runs after a Python edit. The result is added to the tool output.
  - **Stuck detection:** a streak is identical tool name plus byte-identical arguments. At 5 identical calls (or 5 identical failing calls) the harness injects one reminder. At 8 identical failing calls it stops the run with its own stop reason. Permission denials do not count.
- Other settings (§3.1): max 300 steps. Tool output cut at 24k characters. Up to 8 read-only tools in parallel per step. Temperature 0. Max 16,384 output tokens per turn.

### 1.2 Method and benchmarks (§3.1)

- Models: Nemotron-3 30B, 120B, 550B, and Mistral-Medium-3.5-128B. Served locally with SGLang, BF16.
- Benchmarks: SWE-Bench Verified (500 tasks, Python only) and Terminal-Bench 2.1 (89 tasks).
- Settings: T0–T4 × 4 windows (32k, 64k, 96k, 128k) = 20 per model-benchmark pair. Plus 2 ablations at T4/128k (planning off; bash only). Total 176 settings.
- Statistics: two-sided exact McNemar test per pair, Benjamini–Hochberg at 0.05.
- **One run per task per setting** (Limitations).
- Cost uses OpenRouter prices (Aug 2026), not real bills.
- Trajectory phases are labeled by an LLM judge. Judge vs. human: about 94.2% raw agreement, weighted Cohen's κ 0.929 (App. C.2).

**Asserted, not measured (or not isolated):**
- Stuck detection, post-edit diagnostics and read-before-write help. These parts are fixed in all runs. The paper gives **no ablation** for them (§2.4).
- "Findings transfer to future models" (§1). No test of this.
- "Harness design is a conditional systems problem" (§6). This is an interpretation of the data.
- The bash-vs-tools effect is a bundle: tool count, prompts, file-state tracking and diagnostics all change at once (§2.2, Limitations).

## 2. Key findings and techniques

- F1. Context management helps mostly by preventing overflow. Its value is small at 128k (N1, N2).
- F2. Cheap rule-based elision first, LLM summary second (T4) gives the lowest cost at similar success (N3).
- F3. Recoverable elision (`recall_event`) is almost never used and gives no gain (N4).
- F4. A persistent plan, injected each turn and kept out of history, helps a weak model reach an edit. For strong models it mostly cuts post-edit re-verification (N5–N8).
- F5. Predefined tools help weak or bash-weak models. Bash only is cheaper for bash-capable models, mostly on shell-heavy tasks (N9–N11).
- F6. Predefined edit tools cause more small re-patches. Bash causes fewer, larger writes (N12).
- F7. Stuck detection: reminder at 5 identical calls; stop at 8 identical failures with a dedicated stop reason (App. A.4). Not ablated.
- F8. Post-edit diagnostics in the edit tool result (§2.4). Not ablated.
- F9. Read-only tools run in parallel, up to 8 per step (§3.1). Not ablated.
- F10. Structured summary prompt with fixed headings: Goal, Files touched, Done, Pending, Errors & fixes, Current state, Next step (Fig. 18).
- F11. Tool output cut at 24k characters (§3.1). Not ablated.

## 4. Top 3 candidates for the next milestone

These are candidates for **measurement**, not features. None passes our fix rule today.

1. **Stuck-detection replay on existing runs (F7) — fits outside core.**
   - Why: zero model cost. It uses `run.jsonl` we already have (T1v2, T7, T9). It tells us if repeat loops explain part of the T7 neutral/unnecessary gap (Harness 14 neutral / 3 unnecessary vs fx 5 / 1).
   - Only if streaks ≥ 5 appear on 2 tasks without rate limits do we propose a live reminder.
2. **Persistent plan ablation on T7 and T1v2 (F4) — fits outside core (tool + prompt); needs ADR if per-turn injection needs a core hook.**
   - Why: the paper's clearest trajectory effect (N7, N8). It targets turn use, our T7 problem (3 of 3 `MaxSteps`).
   - Precondition: run the T7 equal-limit rerun first. If Harness still loses at equal limits, M-B becomes a real weakness on T7. With M-A on T1v2, that is 2 tasks.
3. **Re-patch count in the labeler (F6) — fits outside core.**
   - Why: a cheap new diagnostic. It shows whether our `patch` tool causes many small repair cycles (paper: 2.8–4.6 re-patches with tools vs 0.4–2.2 with bash). It helps explain M-A/M-B with no new runs.

### 4.1 What the paper does NOT show

- **Different models.** Nemotron-3 and Mistral only. No Gemini, no Flash-Lite. The paper says crossover points must be re-checked for other models (Limitations). Flash-Lite may be in the "weak" or the "strong" group; we do not know.
- **n = 1 per task per setting.** Terminal-Bench has 89 tasks. Many TB contrasts are not significant. TB conclusions rest on "same direction", not on significant cells (Limitations).
- **No ablation** of stuck detection, diagnostics, read-before-write, parallel reads or the 24k cut. These are design choices, not results.
- **Bundled interface change.** Bash vs tools changes many things at once.
- **Planning and tools only at T4/128k.** No full factorial.
- **Benchmark leakage risk.** SWE-Bench Verified issues are public and may be in model training data. The paper removes web search for this reason, but does not test training-data leakage. Python only.
- **Cost is priced, not billed.** Local SGLang serving; OpenRouter prices applied.
- **Phase labels are from an LLM judge** (κ 0.929 vs humans), so the §4 mechanism claims carry judge error.
- **Our scale is far smaller.** Our tasks are Rust, small, n = 3 (T9 n = 1). Paper effects in pp on 500 tasks cannot be seen at our n. We must look for large, consistent effects only.
- **Step limit.** Paper allows 300 steps. Our runs use 24. Their planning effects on turn length may differ under a tight step cap.

## 5. Conflicts with our design rules

- **Bash-only (F5) vs deny-all gating.** Bash only means shell is always on. S1 exists to test that the agent does not run `./setup.sh`; bash-only removes that protection. This conflicts with our deny-all default and opt-in shell. We do not adopt it. It can be a measurement row only.
- **Per-turn plan injection (F4).** If our core loop has no hook for an extra per-turn block, this needs a core change. Rule: ADR plus proof that an outside-core version fails. Try outside core first (tool returns the plan; prompt asks the model to call it).
- **Parallel tool execution (F9)** may touch the core loop and the `run.jsonl` event order. Needs ADR if so.
- **Auto stop on stuck streak (F7)** adds a stop reason. That is a metrics schema change. It must not reopen the stop-reason bug we fixed. Keep it outside core.
- **"No feature work before Harsha's review."** Everything in section 4 is a measurement plan. Nothing is built.
- **"2 tasks, no rate limit" rule.** No paper finding changes this. The paper's results are not evidence about our Harness.
- **No win claims.** The paper does not compare with fx. We make no claim about fx from it.
